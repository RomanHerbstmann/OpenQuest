# ADR-0008: The phone app is a Capacitor shell around the web frontend

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-26 |
| Decider | Backend developer (hackathon team) |
| Related | [ADR-0002](0002-tree-photo-verification.md) (photo verification), [docs/mobile-app.md](../mobile-app.md) |

## Context

Players walk to a tree and photograph it. In the browser this is the weakest part of the app: `getUserMedia` needs HTTPS and a permission
dialog on every visit, behaves differently in every mobile browser, gives a live preview in a web page with a low frame rate and no
autofocus/HDR/flash of the real camera app, and fails in in-app browsers. The phone's own camera gives better photos (which the
photo verification needs) and a familiar flow. GPS has the same problems (permission per site, no background use, inaccurate in browsers).

## Decision

Package the existing Next.js frontend as an app with **Capacitor** (Android and iOS) instead of writing a second, native player app.

- The frontend is exported statically (`MOBILE_BUILD=1 next build` → `out/`) and loaded by the app's web view; the web build for the browser
  stays as it is. One UI code base for web and phones.
- Inside the app the **native camera** (`@capacitor/camera`, JPEG, longest side 2048 px, orientation corrected) replaces the browser camera
  in the scan dialog, and the **native GPS** (`@capacitor/geolocation`) replaces browser geolocation. Both are wrapped in `src/lib/camera.ts` and
  `src/lib/position.ts`; in the browser the old code paths run unchanged (`isNativeApp()` decides).
- The web view runs under `https://localhost` (Android, `androidScheme: 'https'`) and `capacitor://localhost` (iOS). The API allows both
  origins in CORS. The app needs the API's full address (`NEXT_PUBLIC_API_URL`) because it has no origin of its own.
- The native projects (`android/`, `ios/`) are generated by `cap add` (`pnpm mobile:init`) and committed. `scripts/mobile-native-setup.mjs`
  adds the permissions (camera, photos, location) idempotently.
- App id `fun.openquest.app` (the project's domain, openquest.fun).

## Alternatives considered

- **PWA only:** installable, but the camera and GPS stay the browser's; that is the problem we want to solve.
- **Native apps (Kotlin/Swift) or Flutter/React Native:** best camera control, but a second UI to build and keep in step in a hackathon.
- **`<input type="file" capture>`:** already used as a fallback; opens the camera app but only works well on some browsers and gives no control over size and orientation.

## Consequences

- Building needs Node 20+, JDK 17 and the Android SDK for Android, a Mac with Xcode 16 for iOS. CI does not build the apps.
- Changes to the web frontend reach the app only after `pnpm mobile:build` and a new install; store releases need signing keys and store accounts (not part of this ADR).
- The frontend must not rely on server features (API routes, server actions, image optimization), because the app is a static export. Dynamic routes need `generateStaticParams` (the lexicon already has it).
- The app talks to the API over the network; offline use is not supported yet.
